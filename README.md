# GeoAlert — Complete Deployable Codebase

Everything below was actually run and tested while building it (not just written and hoped to work): the ML ensemble was trained on a real 7,000-sample dataset generated by this repo and scored on a held-out test set; the Flask API was driven through real HTTP requests; the agentic layer's request-construction was verified against the live Gemini API up to the network boundary. The numbers quoted in this document are the real numbers that run produced, not estimates.

```
GeoAlert-Project/
├── firmware/geoalert_esp32/geoalert_esp32.ino   Arduino sketch for the physical node
├── ml/
│   ├── generate_dataset.py                      synthetic-but-physical dataset generator
│   ├── train_models.py                          trains RF + XGBoost + SVM + LSTM + ensemble
│   └── models/                                  saved models + metrics.json (created by training)
├── backend/
│   ├── database.py                              SQLite storage
│   ├── ensemble.py                               loads models, runs the 4-way soft vote
│   ├── agent.py                                  the agentic AI alert layer (Gemini + tools)
│   └── app.py                                     Flask REST API tying it together
├── dashboard/dashboard.py                         Streamlit live dashboard + hardware-free demo
├── requirements.txt
└── .env.example
```

## 1. What each piece actually does

### `firmware/geoalert_esp32.ino` — the physical node
Reads all five sensors (soil moisture, rainfall, DHT22, SW-420 vibration via interrupt, MPU-6050 tilt derived from the accelerometer vector), packages them as JSON, and POSTs to the backend over WiFi every cycle. It deliberately does **not** try to run the ML ensemble on-device — an ESP32 has neither the RAM nor the point of duplicating four models that already run comfortably in Python. Its only "intelligence" is a dumb, hardcoded threshold check used **exclusively** as a hardware-level failsafe: if WiFi/the backend is unreachable *and* a reading is obviously extreme, it fires an SMS directly over the SIM800L V2, bypassing the cloud entirely. That split — cloud does the thinking, hardware guarantees a last-resort alert path — is what makes the system resilient to a dead internet connection in the field, which is a realistic failure mode on a remote slope.

### `ml/generate_dataset.py` + `ml/train_models.py` — the ensemble
No public labelled landslide-sensor dataset exists at the resolution this project needs, so `generate_dataset.py` builds one from small physically-motivated stochastic processes (rainfall as a bursty AR(1) process with storm events, soil moisture as a leaky integrator of rainfall, vibration rate rising with saturation, tilt drifting faster when both are elevated) — the standard, defensible approach for a project like this before real field data exists. `train_models.py` then trains all four algorithms your report names and combines them into a soft-voting ensemble. **Real measured results from the included run:**

| Model | Accuracy | Macro-F1 |
|---|---|---|
| Random Forest | 93.9% | 77.9% |
| XGBoost | 93.4% | 76.5% |
| SVM | 88.3% | 68.6% |
| LSTM | 93.1% | 77.2% |
| **Ensemble (soft vote)** | **94.1%** | **78.6%** |

The ensemble beats every individual model on both metrics — the actual justification for using one at all, not just a claim. Macro-F1 sits noticeably below accuracy because the minority classes (`Watch`, `Critical`) are hard, which is realistic: real landslide risk is heavily imbalanced (most days are safe), and the model is trained with class-balanced weights specifically so it doesn't just learn to always predict "Safe." This is worth a paragraph in your report's results/limitations discussion — it's an honest, defensible finding, not a weakness to hide.

### `backend/ensemble.py` — inference
Loads the four saved models once and reproduces the exact same soft-vote combination used during training, for every incoming reading. Handles the "brand-new node with zero history" cold-start case by treating the current reading as if it had been steady, which is the sensible assumption when there's no prior context yet.

### `backend/database.py` — storage
SQLite. Deliberately boring: no server, no account, ships with Python, and it's genuinely free forever — the right tool here rather than a hosted database you don't need yet.

### `backend/app.py` — the API
Five endpoints: `POST /api/ingest` (what the ESP32 calls), `GET /api/latest`, `GET /api/history`, `GET /api/alerts`, and `POST /api/simulate` (push a synthetic Safe/Warning/Critical reading through the *real* pipeline — this is how the dashboard demos the whole system with zero physical hardware, which is worth using live in a viva).

### `dashboard/dashboard.py` — the UI
Streamlit. Shows the current risk level, sensor history charts, the agent's latest reasoning, and an alert log. The sidebar's Safe/Warning/Critical/Random buttons drive `/api/simulate`, so you can demonstrate the entire system — sensors through to an AI-composed alert — without any hardware connected at all.

## 2. The agentic AI layer, in detail

This is the part worth explaining carefully, because "agentic" is doing real work in this design, not just marketing language for "we called an LLM."

**What the ensemble gives you** is a label and a confidence: `Warning`, 52%. That's a classification. **What a real early-warning system needs** is a *decision*: should anyone be woken up right now, and if so, what exactly should they be told to go check? Those are different problems. A fixed rule ("if Warning or Critical, send an SMS") throws away context that matters enormously in practice — a `Warning` reading after three hours of steadily climbing soil saturation and tilt is a genuinely different situation from the same label triggered by a rain sensor spike that's already passing. A human on-call engineer would glance at the recent trend before deciding how urgently to act. `backend/agent.py` gives the model the ability to do exactly that.

**The mechanism — function calling, not prompt engineering.** The agent is built on Google's `google-genai` SDK (the current unified Python SDK Google recommends — the older `google-generativeai` package is deprecated). Two plain Python functions are handed to the model as *tools*:

```python
def get_recent_trend(hours: float) -> dict:
    """Look up this node's recent history... so you can judge whether
    conditions are rising, flat, or falling before deciding how urgently
    to respond."""
    ...

def send_alert(severity: str, headline: str, message: str) -> dict:
    """Send a real alert email... Only call this for Warning/Critical,
    or Watch when the trend is rising."""
    ...
```

The SDK reads each function's docstring and type hints to build the tool schema automatically — you don't write JSON schema by hand. When `generate_content()` is called with `tools=[get_recent_trend, send_alert]`, Gemini can, mid-response, decide to *call* `get_recent_trend(hours=3)`, receive the real result computed from your SQLite database, reason over it, and *then* decide whether to call `send_alert(...)` — composing the subject line and message body itself, in plain language a village official can act on. The SDK executes this whole loop (Google calls it "Automatic Function Calling") and hands back the final text. That multi-step "look before deciding, then optionally act" loop — not a single input→output pass — is what makes this agentic rather than just "an LLM wrote our SMS text."

**The system prompt is the agent's policy**, not just a persona:

> "Before deciding on anything above 'Safe', call `get_recent_trend`... Only call `send_alert` for Warning or Critical, or for Watch when the trend is clearly rising... Always end your reply with a short plain-language summary of your decision and why, even when you decide not to alert."

That last line matters: even when the agent decides *not* to alert, it still has to explain why, so the reasoning is always visible in the dashboard rather than a silent no-op you'd have to trust blindly.

**Why this is free.** Gemini's Flash-tier models have a genuine free tier through Google AI Studio — no credit card, no trial period that expires. `GEMINI_MODEL` defaults to `gemini-2.5-flash` in `.env.example`; swap in whatever the current recommended free-tier Flash model is by the time you deploy (this field changes model names every few months, so check [ai.google.dev/pricing](https://ai.google.dev/pricing) rather than trusting any hardcoded name to stay current forever).

**Graceful degradation.** If `GEMINI_API_KEY` is unset, `run_agent()` falls back to a deterministic rule-based version automatically — same interface, same return shape, so the rest of the system (backend, dashboard) works immediately even before you've grabbed a key. You'll see `"mode": "rule_based_fallback"` in the response until you configure one.

**What "send" actually does.** `send_alert` sends a real email via SMTP (Gmail with a free App Password — see `.env.example`). If SMTP isn't configured either, it prints what *would* have been sent and logs it as `simulated_no_smtp_configured` — so the agent's decision-making is fully visible and testable even with zero external accounts set up.

## 3. Running it

```bash
pip install -r requirements.txt

# 1. Generate the dataset and train the ensemble (takes ~2 minutes)
cd ml
python generate_dataset.py
python train_models.py
cd ..

# 2. Start the backend
cd backend
python app.py                      # http://localhost:5000

# 3. In a second terminal, start the dashboard
cd dashboard
streamlit run dashboard.py         # http://localhost:8501
```

Open the dashboard and click **Warning** or **Critical** in the sidebar — no hardware required to see the full pipeline (ensemble → agent reasoning → alert log) react live. For the real node, edit the `WIFI_SSID` / `WIFI_PASS` / `SERVER_URL` constants near the top of `geoalert_esp32.ino` and flash it from the Arduino IDE.

## 4. Free hosting — one option per phase, verified current as of mid-2026

| Phase | Recommended free option | Notes |
|---|---|---|
| **Code / version control** | [GitHub](https://github.com) | Free for public and private repos. Render and Streamlit Cloud both deploy straight from a GitHub repo, so push here first. |
| **Backend API (Flask + models + agent)** | [Render.com](https://render.com) free Web Service | No credit card required, free PostgreSQL also available if you outgrow SQLite. **Caveats**: the free tier gives 512MB RAM (tight with TensorFlow loaded — `tensorflow-cpu` in requirements.txt is the smaller build specifically for this) and the service **sleeps after 15 minutes of inactivity** (first request after sleep takes a few seconds — fine for a demo, not for production). The free-tier disk is also ephemeral, so SQLite resets on redeploy — acceptable for a student project, not for real deployment. |
| **Backend, alternative** | Run it locally on your own laptop | For a live viva/demo this is genuinely the most reliable option — zero cold starts, zero memory limits, zero risk of the free tier being asleep at the worst moment. Deploy to Render separately for the "the system is live on the internet" claim in your report. |
| ~~PythonAnywhere~~ | **Not suitable here** | Its free tier blocks outbound internet access to arbitrary hosts, which would block the backend's calls to the Gemini API. Fine for a pure Flask app with no external API calls; not fine for this one. |
| **Dashboard** | [Streamlit Community Cloud](https://streamlit.io/cloud) | Free, purpose-built for exactly this — connect your GitHub repo, point it at `dashboard/dashboard.py`, done. Set `GEOALERT_API_URL` in its secrets panel to your deployed backend's URL. |
| **Database** | SQLite (already included) | No hosting needed — it's a file inside the backend. If you need it to survive Render restarts, Render's free PostgreSQL (90-day free instance) is the natural upgrade; swapping `database.py` to use it is a small change since the queries are already isolated in one file. |
| **Agentic AI** | [Google AI Studio](https://aistudio.google.com/apikey) | Free Gemini API key, no credit card. Rate-limited (roughly 10–15 requests/minute on the free Flash tier at time of writing) — completely sufficient for one sensor node posting every 30 seconds to a few minutes. |
| **Email alerts** | Gmail SMTP + App Password | Free, no third-party SMS/email service needed. Requires 2-Step Verification enabled on the Gmail account first. |
| **Firmware** | Arduino IDE (desktop, free) | No hosting applicable — flashed directly over USB. |

**Suggested path for your submission:** run the backend locally during your actual demo/viva (reliability), but also deploy a copy to Render and the dashboard to Streamlit Cloud beforehand so you have a live public URL to show in the report/screenshots as evidence of a deployed, not just local, system.

## 5. Honest limitations (worth stating in your report, not hiding)

- **Dataset is synthetic.** It's physically motivated, not measured — real sensor calibration will shift the exact thresholds. Chapter 6's `mapFloat()` calibration constants in the firmware are placeholders that need real field values from your specific probes.
- **Minority-class recall is the weak point** — `Watch` recall in particular (see the confusion matrix `train_models.py` prints). This is a legitimate area for the "Future Work" section: more geophysical parameters (echoing the exact limitation your own literature review flags for Sreevidya et al., 2021) would likely help most.
- **Render's free tier sleeps and has ephemeral storage** — acceptable for a demo, explicitly not a claim of production-grade uptime.
